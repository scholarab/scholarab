# ScholarAB database and codebase audit

Reviewed 2026-09-09 at commit `a756921`. This is a remediation plan, not an implementation. Database inspection was read-only; no records were changed and no emails or deployments were triggered.

ScholarAB is an Alberta scholarship and research-program directory. Astro prerenders the public pages from committed JSON; vanilla browser controllers handle directories and saved items, and React handles the eligibility quiz and admin panel. Cloudflare serves the static site and API routes. Neon Postgres holds the admin catalogue, subscriptions, anonymous analytics, and rate-limit counters. GitHub Actions expires listings, mirrors JSON into Postgres, checks links, sends reminders, and prunes records.

The most valuable work is correcting the publishing/data-identity split, fixing admin truncation and quiz geography, and making destructive tools and email operations reliable. Current database size does not justify a database replacement or broad indexing project.

There are 2,650 events and 37 subscriptions: 31 confirmed and 6 unconfirmed. No unconfirmed subscription was older than 30 days. Aggregate counts only were inspected for subscribers; email addresses and tokens were not exported.

The safe invocation `node --env-file=.env.local --import tsx scripts/sync-db.ts --dry-run` reports zero inserts and zero updates across both catalogues. Their mirrored fields currently agree by name. Identity still does not agree, and one of the eight extra scholarship rows is active.

Examples: Medicine Hat College Student Awards is JSON ID 2 / DB ID 176; HYRS University of Alberta is JSON ID 1 / DB ID 20. JSON program ID 20 means Tate High School Internship, while DB ID 20 means HYRS. Public subscription APIs and the sender currently resolve against JSON, which avoids directly mixing these identities.

## Prioritized correctness findings

P1 = fix promptly because it loses work, hides listings, bypasses an intended protection, or risks destructive behavior. P2 = important reliability/correctness work. Static findings below identify a reachable code path; they do not claim that a production incident has already occurred.

### F1 · P1 · Dry-run can delete database rows

Evidence: [scripts/sync-db.ts:279](/Users/admin/scholarab/scripts/sync-db.ts:279). Inserts and updates check `!DRY`, but the prune block only checks `PRUNE`. Consequently `--dry-run --prune` executes the extra-row and twin DELETE loops. Eight current extra scholarship rows make this more than an empty-database edge case. The destructive combination was not executed.

Fix: make planning and execution distinct. Generate one typed change set; dry-run only prints it, including proposed deletions. Require complete, validated, nonempty inputs before constructing a prune plan. Apply the validated plan transactionally where practical.

Acceptance: test all four combinations of dry-run/prune with a recording DB stub; both dry-run combinations perform zero INSERT/UPDATE/DELETE calls. Test empty/truncated inputs and rollback on failed application.

### F2 · P1 · Admin “Publish to site” does not publish admin edits

Evidence: [AdminShell.tsx:24](/Users/admin/scholarab/src/components/admin/AdminShell.tsx:24), [deploy.ts:13](/Users/admin/scholarab/src/pages/admin/api/deploy.ts:13), [package.json](/Users/admin/scholarab/package.json), [sync-db.ts](/Users/admin/scholarab/scripts/sync-db.ts), and [ci.yml](/Users/admin/scholarab/.github/workflows/ci.yml). CRUD writes Postgres; publishing only calls a deployment hook; builds explicitly blank DATABASE_URL and read JSON. CI mirrors JSON back into Postgres on push/schedule/manual runs, overwriting unexported admin edits.

Fix: retain JSON as the published source initially. Immediately make the admin's draft/unpublished state explicit and remove the misleading success promise. Then implement a validated export/diff workflow from admin drafts to committed JSON, carrying JSON-only fields through unchanged. Publish a specific revision and expose its deployment result. Separate drafts from the mirror so syncing published data cannot erase unfinished edits.

Acceptance: edit/create/delete a fixture through admin, publish it, and verify the rendered site, search index, quiz, and reminder lookup all use that revision. Failed publication retains the draft and reports failure. Subsequent sync does not erase draft work.

### F3 · P1 · Two incompatible catalogue ID systems

Evidence: live read-only reconciliation above; [sync-db.ts:164](/Users/admin/scholarab/scripts/sync-db.ts:164) inserts without JSON IDs and updates by normalized name. Thus an ID cannot safely join a subscription/event to a catalogue row. This is a confirmed integrity limitation; current JSON-based reminder lookup is not evidence of wrong-recipient emails.

Fix: introduce an explicit unique public ID on each catalogue table, backfilled from a reviewed mapping, and keep the existing DB primary key for admin references. Make API types distinguish public IDs from internal row IDs. Use public IDs for analytics/subscription resolution. Match syncs by this stable identity after the one-time reconciliation; renaming a listing must not create a second identity. Review/archive extras separately.

Acceptance: every published JSON item maps exactly once; rename preserves identity; an unrelated row occupying the same numeric DB ID cannot be selected accidentally. Preserve existing browser saved IDs, subscription IDs/tokens, and public URLs. Do not blindly renumber tables or add foreign keys to the current internal IDs.

### F4 · P1 · Admin loses 86 scholarships after its first refresh

Evidence: [admin-crud.ts:35](/Users/admin/scholarab/src/lib/admin-crud.ts:35) caps GET at 1,000. [admin/scholarships.astro:12](/Users/admin/scholarab/src/pages/admin/scholarships.astro:12) initially loads all 1,086. [ScholarshipManager.tsx:43](/Users/admin/scholarab/src/components/admin/ScholarshipManager.tsx:43) replaces that list with the API response every 60 seconds when no modal is open. The 86 omitted rows disappear from client search and pagination.

Fix: implement one consistent server pagination/filter contract for initial load and refresh, with total count and deterministic `updated_at DESC, id DESC` ordering. A temporary complete-list response removes the immediate truncation, but should not become the long-term pagination design.

Acceptance: with 1,086 fixture records, every record remains reachable before and after refresh; searches can find the oldest record; tied timestamps do not duplicate or skip items across pages.

### F5 · P1 · Quiz ignores additional eligible cities

Evidence: [EligibilityQuiz.tsx:281](/Users/admin/scholarab/src/components/EligibilityQuiz.tsx:281) drops `alsoOpenTo` when creating match inputs, and [eligibility-matcher.ts:23](/Users/admin/scholarab/src/lib/eligibility-matcher.ts:23) checks only the primary region. Facet pages already support the field. A local probe with real scholarship 496, Ambassador Scholarship, confirms a Beaumont profile is rejected with “Only for students in Leduc” despite `alsoOpenTo: ['Beaumont']`. Nineteen active city-specific records have secondary eligible cities; individual student eligibility still depends on their other criteria.

Fix: carry `alsoOpenTo` through the match input and share a geographic eligibility predicate between relevant consumers. Keep broad directory scope filters separate from eligibility rules. Check known geography even when structured eligibility is null: currently the early return bypasses region too.

Acceptance: real-data fixtures for Beaumont/Leduc and Chestermere/Airdrie; primary and additional cities pass geography, unrelated cities fail, unknown structured criteria do not erase known location restrictions. Preserve conservative handling of unanswered personal questions.

### F6 · P1 · Confirmation-email cooldown races under concurrency

Evidence: [alert.ts:37](/Users/admin/scholarab/src/pages/api/alert.ts:37) counts prior sends; [alert.ts:204](/Users/admin/scholarab/src/pages/api/alert.ts:204) then sends externally, and only afterward records `confirmSentAt`. Parallel requests for one email and different items can all read zero recent sends. The atomic IP limiter limits each IP's attempts, but does not make the per-recipient cooldown atomic. The scheduled confirmation sweep has a similar select/send/update separation.

Fix: atomically reserve recipient send eligibility before sending, using a shared recipient-level counter/claim used by both the API and sweep. Track pending/sent/failed states so failures can retry without reopening an unbounded concurrency window.

Acceptance: synchronized concurrent signups for the same test address across different items and simulated IPs produce at most the allowed number of outbound calls. API/sweep overlap obeys the same cap. Test retry after provider failure without sending real emails.

### F7 · P2 · Existing reminder settings can be changed without ownership proof

Evidence: [alert.ts:150](/Users/admin/scholarab/src/pages/api/alert.ts:150) updates cadence on `(email,itemType,itemId)` conflict before asking for any token; confirmed rows retain confirmation. Knowing the address and listing is sufficient to alter an existing subscriber's schedule. The response also exposes whether that subscription is confirmed.

Fix: require a subscription credential for editing an existing confirmed reminder, or stage changed settings until a confirmation link is followed. Public signup should return a neutral response and leave confirmed settings intact.

Acceptance: anonymous resubmission cannot change a confirmed row; a token-authenticated update can; generic public responses do not distinguish a known confirmed subscriber.

### F8 · P2 · Optimistic locking is not atomic

Evidence: [admin-crud.ts:99](/Users/admin/scholarab/src/lib/admin-crud.ts:99) SELECTs and compares a timestamp, then [line 112](/Users/admin/scholarab/src/lib/admin-crud.ts:112) UPDATEs by ID alone. Two writers can both pass the comparison and overwrite each other. The version is also optional, and bulk parsing omits it.

Fix: use a required integer revision and a single conditional `UPDATE ... WHERE id = ? AND revision = ?`, incrementing the revision on success. Return 409 for a stale revision and distinguish missing rows. Apply the same contract to bulk edits.

Acceptance: two concurrent edits using one revision produce exactly one success and one conflict. Test missing versions and bulk edits concurrent with manual edits. No partial field changes on conflict.

### F9 · P2 · Deploy-hook HTTP errors are reported as success

Evidence: [deploy.ts:15](/Users/admin/scholarab/src/pages/admin/api/deploy.ts:15) does not check `response.ok`. A local mocked 503 response produced HTTP 200 with `{success:true}`. Admin then displays “Site will be live in ~90 seconds.”

Fix: reject non-success upstream statuses, normalize the success response rather than spreading arbitrary upstream fields, add a timeout, and distinguish trigger acceptance from a completed deployment.

Acceptance: upstream 401/429/500/503, malformed bodies, and timeout never produce a success toast; a valid accepted deployment returns its identifier where available.

### F10 · P2 · Bulk eligibility parsing reports failed saves as completed

Evidence: [ScholarshipManager.tsx:253](/Users/admin/scholarab/src/components/admin/ScholarshipManager.tsx:253) awaits the save fetch but never checks its status, then updates local state. A successful AI parse followed by a failed database save appears saved. The parser also spreads unvalidated model JSON into defaults rather than validating it against `eligibilitySchema`.

Fix: validate parsed AI output at the boundary; inspect each save response, send the row revision, and update UI from the returned saved row. Count parsing failure, save failure, and conflict distinctly; allow failed items to retry.

Acceptance: a parse-200/save-500 sequence does not mark the row tagged; malformed model output returns a controlled error; conflicts preserve the user's newer edit.

### F11 · P2 · JSON null crashes public endpoints

Evidence: [alert.ts:69](/Users/admin/scholarab/src/pages/api/alert.ts:69) and [event.ts:67](/Users/admin/scholarab/src/pages/api/event.ts:67) destructure the parsed body without checking it is an object. Local probes confirm both throw TypeError for a valid JSON `null` body.

Fix: validate object shape before destructuring, ideally with shared boundary schemas. Normalize malformed JSON errors on admin CRUD routes too. Strictly validate complete positive integer IDs instead of permissive `parseInt` path handling.

Acceptance: null, arrays, scalars, malformed JSON, invalid IDs, and oversized fields return documented 4xx responses rather than unhandled exceptions.

### F12 · P2 · Reminder delivery has no durable deduplication

Evidence: [send-alerts.ts](/Users/admin/scholarab/scripts/send-alerts.ts) sends every matching milestone on every run, with no delivery ledger or idempotency key; [email-alerts.yml](/Users/admin/scholarab/.github/workflows/email-alerts.yml) permits manual runs and has no concurrency group. Retrying a partially failed job repeats already successful emails. This is a reachable failure mode, not a claim that duplicates have been observed.

Fix: persist a delivery record keyed by subscription, deadline/cycle, and milestone, with atomic claim/status transitions. Use provider-supported idempotency where available and a stable key across retries. Add workflow concurrency as a supplementary guard and explicit semantics for deliberate catch-up sends.

Acceptance: repeat and overlapping runs do not duplicate successful deliveries; a partially failed run retries only unsent messages; an ambiguous provider timeout can be retried safely. A corrected deadline has a deliberate, tested delivery policy.

## Bottlenecks and efficiency plan

### O1 · Reduce admin database round trips first

[admin/analytics.astro:49](/Users/admin/scholarab/src/pages/admin/analytics.astro:49) performs nine independent queries sequentially. It repeatedly aggregates the same events table and fetches two full title maps. A read-only `EXPLAIN (ANALYZE, BUFFERS)` of the monthly aggregation over 2,650 events took **2.463 ms**, used a sequential scan, and did not spill to disk. One batch containing this explain and two small count queries took **290 ms** end-to-end from this machine; that is a single local sample, not production latency or a per-query estimate.

Plan: batch or use bounded parallelism for independent reads; combine related aggregates where it simplifies the query; load the requested month and cache short-lived aggregate results. Keep public JSON titles authoritative until F3 is resolved. Measure database execution separately from network time and cold starts. Target no more than two serial DB network stages per dashboard load. At this size, a sequential scan is reasonable; do not add indexes simply because a scan appears.

### O2 · Reduce public HTML and quiz payloads

Measured existing `dist` artifacts, generated 2026-09-09 at 16:25 MDT. These are local file sizes, not measured production transfers or Core Web Vitals. Gzip figures use Node's gzip compressor; deployed encoding may differ.

| Page | Raw HTML bytes | Gzip bytes | Other observation |
|---|---:|---:|---|
| /scholarships/ | 1,923,163 | 241,221 | 1,078 cards; approximately 15,462 opening HTML tags |
| /programs/ | 284,821 | 48,320 | 123 cards |
| /match/ | 2,417,123 | 318,984 | Full catalogue serialized into React props |

Plan: give the quiz a compact, versioned matching/result payload, excluding curator notes and unused prose/metadata, and fetch it once when needed while keeping answers local. For directories, profile filtering and DOM work on a throttled mobile browser; consider accessible pagination/progressive rendering with a compact search index while preserving discoverability and no-JS navigation. Avoid making a thousand hidden cards the permanent scaling strategy.

Proposed acceptance targets, to validate with profiling: reduce quiz embedded data by at least 50%; no filter interaction exceeding 100 ms at the current corpus on the selected reference device. Record initial load, hydration, retained memory, search interaction, and navigation before/after rather than assuming smaller bytes alone solve responsiveness.

### O3 · Avoid repeated filter and DOM work

[directory-client.ts](/Users/admin/scholarab/src/lib/directory-client.ts) recomputes chip counts, writes list context, and checks/moves nodes for every input event. Under filtering, `want.length` includes visible nodes only, while `grid.children.length` includes hidden cards, so the in-order shortcut cannot succeed for an already-filtered unchanged result set.

Plan: compare visible-node order, cache stable DOM references and normalized search data, update only changed attributes/counts, and coalesce rapid input renders. Preserve keyboard focus and screen-reader behavior. Test repeated queries yielding identical results cause no card moves; profile before adding more caching complexity.

### O4 · Batch sync writes and email-recipient reads

[sync-db.ts](/Users/admin/scholarab/scripts/sync-db.ts) executes one HTTP query per changed row; a bulk content refresh can require over 1,000 serial network requests. Current dry-run shows no changes, so this is a bulk-update scaling concern, not an observed slow no-op run. [send-alerts.ts](/Users/admin/scholarab/scripts/send-alerts.ts) queries subscribers separately for each target listing and sends messages serially.

Plan: after identity and dry-run safety fixes, use bounded batches of stable-ID upserts with change detection and transactions, preserving timestamps on unchanged rows. Fetch matching subscriptions in a set-based query. Use bounded, provider-aware send concurrency only after F6/F12 prevent duplicates and recipient-limit bypasses. Benchmark 0/10/1,000 changed rows and failure midway through a batch.

### O5 · Align schema and migration state

The live DB has `timestamptz` for all three subscriber timestamps, while [schema.ts](/Users/admin/scholarab/src/lib/db/schema.ts) declares plain `timestamp`. Live indexes `subscribers_item_idx` and `subscribers_unconfirmed_idx` are absent from that schema. `research_programs.active` is NOT NULL live but nullable in the declaration. Audit/deploy/mutation log tables remain live outside the current declared schema.

Plan: align declarations with live types and indexes, inventory intentional historical objects, then establish a migration ledger/checksum and read-only drift check. Follow [migrations/README.md](/Users/admin/scholarab/drizzle/migrations/README.md): the journal is stale, so do not run blind Drizzle generation/migration. Test new database bootstrap and upgrades on an isolated database. Prefer additive migrations and verified compatibility over broad catch-all fallbacks that label every database failure a missing column.

An events timestamp index may become useful for retention/range queries as volume grows, but measure the actual query plan and deletion volume before adding it. The live subscriber item lookup index already exists; adding a duplicate is unnecessary.

## Smaller follow-ups

- [auto-expire.ts](/Users/admin/scholarab/scripts/auto-expire.ts) requires a valid future deadline before reopening an inactive JSON scholarship, but the SQL branch allows null/non-date deadlines. The live database currently has zero rows matching the dangerous reopening case. Share/test the predicate, including curator-retired listings, and update revisions when status changes.
- [prune-events.ts:50](/Users/admin/scholarab/scripts/prune-events.ts:50) deletes orphan events before checking whether catalogue arrays are empty; the later guard protects only subscriptions. Move all input validation before any deletion and give pruning the same plan/dry-run structure as F1.
- [README.md:28](/Users/admin/scholarab/README.md:28) tells contributors to use `open_date`, while the JSON loader/sync consume `openDate`. Correct the instructions and reject or normalize legacy spelling during validation.
- Confirmation email and confirmation-page text always promises 30/14/3-day reminders even when the user selected a different cadence. Render the selected schedule consistently after F7 defines authenticated settings changes.
- Dashboard subscriber counts include unconfirmed rows. Label pending and confirmed separately so “reminders” is not mistaken for deliverable reminders.
- Centralize Alberta calendar-date handling for the browser, Worker, build, and scheduled/manual alert jobs. Current browser/Worker helpers use host-local dates; test Alberta evening/UTC midnight and daylight-saving boundaries. Scheduled 14:00 UTC sends do not by themselves prove a current wrong-day incident.

The publishing product decision is whether admin should remain a draft editor exporting reviewed JSON or become the authoritative content store. The recommended first implementation preserves JSON publishing and adds a reliable draft/export workflow because existing pages, browser saves, reminders, and automation already depend on it. Do not switch builds directly to today's active-only DB loader: it omits inactive/future content and JSON-only fields.

For database changes, take a restorable snapshot and validate mappings on an isolated copy, deploy additive schema before dependent code, and preserve the existing IDs during rollout. For public behavior, use focused regression tests plus browser smoke checks of matching, search, saving, and publishing. Keep email/provider calls mocked until an explicit controlled delivery test is arranged.

Scope adjustments based on implementation evidence:

- A canonical catalogue table holding published snapshots and drafts is safer than making the two historical tables authoritative. The legacy tables remain for recovery and explicit identity mapping; eight unmatched legacy scholarships are excluded from the current catalogue without deletion.
- Publishing uses the existing GitHub/Cloudflare integration and a reviewed queue instead of adding another deploy hook or credential. GitHub schedules are nominally every 15 minutes, not a guaranteed publication SLA.
- Retained-history analytics stay available. The measured database aggregation was already fast, so month-only APIs and speculative new indexes were not added.
- Directory pagination/virtualization was not introduced: after fixing repeated work, sampled filtering met the 100 ms target while preserving all server-rendered cards, searchability, and no-JS navigation. The 1.9 MB raw directory HTML remains a future size concern as the corpus grows.
- Email sends remain serial at the present small volume. Read batching, durable claims and retries deliver the useful improvement without introducing provider-rate bursts. Ambiguous sends past the provider's idempotency window require reconciliation rather than risking duplicate emails.
- Nonbreaking dependency updates reduced npm's advisory count from 16 to 7. The remaining advisories involve Astro, its Cloudflare adapter, and their image/network dependencies; npm proposes major framework/adapter upgrades. Those platform upgrades were deliberately kept out of this data/publishing rollout. They remain an explicit follow-up, not a claim of a clean dependency-security audit.

Verification: 893 tests in 44 files pass in both the local Alberta environment and a UTC run (older implementation-mocking tests were replaced by stronger SQL integration coverage); ESLint is clean; Astro checks 177 files with zero errors/warnings/hints; scripts type checking and full data validation pass. Desktop/mobile smoke tests passed 32 checks with two existing mobile skips. Additive migration 0013 was tested on isolated PostgreSQL, applied live, and its checksum/runtime checks pass. The live catalogue contains 1,078 scholarships and 129 programs with zero drafts/queued requests after seeding. Repeated sync and prune dry-runs make no changes. No emails or sample publications were sent to users during verification.

Performance figures are local measurements, not field Core Web Vitals. Quiz gzip totals exclude separately loaded JavaScript and use Node gzip rather than the deployment's negotiated compression. Filter timings measure synchronous input handlers in headless Chromium at a 390×844 viewport with 4× CPU throttling, not complete interaction-to-next-paint latency. The production draft-to-live workflow itself has not been exercised with a real editorial change; its queue, merge/conflict, and persistence contracts are covered by isolated tests.
